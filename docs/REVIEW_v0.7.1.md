## 判定：不合格（要修正）

### 根拠

- アプリの中核価値である「忘却曲線でメモが浮上する」仕組みが、端末時刻の前方ジャンプ1回で**恒常的に停止しうる**欠陥（S-1・重大）が残っている。利用者は気づけず、アプリ内から回復する手段もない。
- データ消失そのものは起きにくい作り（保存の原子性・復旧経路は健全）だが、Undo の仕組みに「編集を黙って巻き戻す」「前の操作の復元機会が黙って消える」という、中核の片づけフローで踏みやすい欠陥（S-2／S-3・中）が2件ある。
- 上記以外は良好。前回の指摘14件＋R-1〜R-3 の解消状態は維持され、SPEC の不変ルール、ART_DIRECTION の数値基準（コントラスト4.5:1以上・最小12sp・赤不使用）は静的確認の範囲で守られている。

## 指摘一覧

### S-1時刻ガードの前方ジャンプで忘却曲線が恒常停止する

- 根拠：`MemoStore.kt` の `effectiveNow()` / `advanceClockGuard()`、`init` での `advanceClockGuard(System.currentTimeMillis())` 呼び出し、`maxSeen` の JSON ルートへの永続化。
- 再現条件：
1. 端末の日付を大きく先へ進める（例：1年後）→ アプリを開く。この時点で `maxSeen` が未来時刻に更新され、次の保存で永続化される。
2. 端末の日付を正しい時刻に戻す。
3. 以後、`effectiveNow()` は永遠に未来の `maxSeen` を返し続けるため、新規メモは `isFresh` のまま節目に到達せず、既存メモも「またあとで」を押した後は `lastReviewedAt = maxSeen` となり二度と浮上しない。実時間が `maxSeen` に追いつくまで（1年ジャンプなら約1年）復旧しない。
- 何が問題か：後方ジャンプ対策として入れたガードが、前方ジャンプに対しては逆効果になる。状態表示は `maxSeen` 基準で自己整合して見えるため利用者は異常に気づけない。ジャンプ量が2日でも、その期間は曲線が止まる。コンセプトの根幹（時間経過で浮上する）が黙って死ぬ。
- 解消条件：前方ジャンプを検出してガード値を実時間側へ引き戻す、または `maxSeen` の採用に上限（例：実時間＋許容誤差）を設けるなど、前方ジャンプ後に実時間へ復帰できる設計にし、その回帰テストを追加すること。

### S-2Undo の全スナップショット復元が、操作後の本文編集を黙って巻き戻す

- 根拠：`MainActivity.kt` の各操作ハンドラ（操作**前**のメモ全体を `postNotice` のスナップショットとして保持）と `MemoStore.kt` の `restoreSnapshot`（ID 一致でメモを丸ごと置換）。通知タイマーはホーム表示中のみ進み（`LaunchedEffect(notice?.id, onHome)`）、詳細画面から戻ると 4.5 秒が再カウントされる。
- 再現条件：
1. ホームでメモに「またあとで」等の通知付き操作をする（バナー表示）。
2. バナーが出ている間に同じメモの詳細を開き、本文を編集する（自動保存される）。
3. ホームに戻り、バナーの「元に戻す」を押す。
4. メモは操作前のスナップショットに丸ごと戻り、**手順2の編集が無警告で消える**。
- 何が問題か：自動保存を売りにするアプリで、利用者の入力が確認なしに失われる。復元の粒度が「操作した項目だけ」ではなく「メモ全体」であることが原因。
- 解消条件：復元時に操作対象フィールド（reviewStage／lastReviewedAt／enteredActiveAt／willDoAt／lowPriority 等）だけを戻し、本文（body／question／answer）は現在の値を保持すること。または編集が挟まった場合は復元を無効化し、その旨をバナー側で扱うこと。

### S-3通知が単一枠のため、続けて操作すると前の操作の「元に戻す」が黙って消える

- 根拠：`MemoStore.kt` の `postNotice`（既存の通知を無条件に置き換え、`undoLatestNotice` は最新1件のみ対象）。
- 再現条件：
1. メモAに「やった」を実行する（確認ダイアログなし。SPEC §3 が定める唯一の保護はこのバナー）。
2. 4.5 秒以内にメモBへ別の通知付き操作（「またあとで」等）を行う。
3. バナーはメモBのものに差し替わり、メモAの復元手段は無言で消滅する。
- 何が問題か：このアプリの主フローは「複数メモを連続で片づける」ことであり、その流れでは Undo は実質「最後の1操作」しか守らない。特に「やった」は恒久削除で確認ダイアログもないため、誤操作の救済が SPEC の想定より弱い。
- 解消条件：通知を最低限スタック化する、または「やった」の直後に別操作が来ても前の復元機会が残る設計にすること。難しい場合は、少なくとも「やった」の復元機会が差し替えで消えることを設計として明示し、SPEC §3 の「保護された」記述を実態に合わせること。

### S-4キー入力ごとにメインスレッドで全件保存＋fsync が走る

- 根拠：`MainActivity.kt` の EditScreen／WriteScreen は `onValueChange` のたびに `persist` → `MemoStore.editBody/update` → `save()` を同期実行する。`save()` は全メモの JSON 構築、tmp 書き込み、`fd.sync()`、prev コピー、rename までを呼出スレッド（メインスレッド）で完結させる。デバウンス・非同期化・保存の合体（coalesce）はない。
- 再現条件：メモが 50〜200 件（長文含む）の状態で詳細画面で文字入力を続ける → 保存コストが件数・総文字数に比例して増え、入力の引っかかり要因になる。
- 備考：仕組み（同期・全件・毎キー入力）はコードで確定。実際の引っかかりの大きさは実機計測が必要なため、その部分は**仮説**。
- 解消条件：保存をバックグラウンド化する、または入力中は保存を間引き（例：停止後・画面離脱時に確定保存）し、入力応答性が件数に依存しないこと。

### S-5WriteScreen で保存される本文が trim 済みなのに、入力欄は未 trim のまま表示される

- 根拠：`MainActivity.kt` WriteScreen の `onValueChange`（保存値に `trim()` を適用するが、表示状態は入力そのまま）。
- 再現条件：新規メモで先頭・末尾に空白や空行を入力する → 保存データからは黙って落ち、再表示すると画面で見ていた内容と異なる（末尾の空行が消える等）。
- 解消条件：保存と表示で同じ文字列を扱う（入力時点で trim しない、または保存値で表示を更新する）。

### S-6UI_CATALOG #12 の記述と実装のズレ（「使い方を見る」の場所）

- 根拠：UI_CATALOG #12 は「使い方を見る」を「その他」ドロップダウンの項目として記載。実装のドロップダウンは3項目（データを書き出す／データを全て消す／このアプリについて）で、「使い方を見る」は About ダイアログ内にある。SPEC §5.1 の記述は実装と一致している。
- 解消条件：UI_CATALOG #12 を実装どおりに修正する。

### S-7ダークモード非対応が意図であることが文書に明記されていない

- 根拠：テーマは `lightColorScheme` 固定＋システムバーも light 固定で実装上は一貫しているが、SPEC／ART_DIRECTION のどこにも「ダークモード非対応（意図的）」の記載がない。
- 解消条件：非対応を意図として SPEC か ART_DIRECTION に一行明記する（対応する場合はその旨）。

### S-8リリースビルドで R8／難読化・圧縮が無効

- 根拠：`app/build.gradle.kts` の release で `isMinifyEnabled = false`。本アプリは org.json の手書きマッピングでリフレクション依存の直列化がないため、機能面の影響は確認できない。影響は APK サイズと難読化なしに限られる（観察寄り）。
- 解消条件：有効化して回帰確認するか、無効のままにする理由をビルド設定のコメント等に残す。

### S-9保存失敗時に tmp ファイルまで削除され、最新状態のディスク上コピーが消える

- 根拠：`MemoStore.kt` の `save()` 末尾。rename が本経路・代替経路とも失敗した場合でも tmp を削除する。`load()` には tmp からの復旧経路があるのに、その材料を失敗時に自ら捨てている。
- 再現条件：保存時の rename が両経路とも失敗 → その後、次回保存が成功する前にプロセスが終了 → 直前の変更は（tmp に完全なコピーがあったにもかかわらず）失われる。前提条件が重いため軽微。
- 解消条件：置換に失敗した場合は tmp を残す。

### S-10一部メモの parse 失敗が利用者に伝わらず、次回保存で恒久的に消える

- 根拠：`MemoStore.kt` の `parseFile` / `load`。個別に parse できなかったメモは `skipped` として黙って除外され、`.skipped-<時刻>` コピーは作られるが画面には一切出ない。その状態で次に保存が走ると、除外されたメモはファイルからも消える。
- 再現条件：JSON 全体は正しいが一部のメモ要素だけが壊れているファイルを用意して起動 → そのメモは無言で一覧から消え、書き出し（メモリ由来）にも含まれない。
- 解消条件：skipped が発生したら、復旧バナー等で「一部のメモを読み込めなかった」ことと書き出し導線を利用者に知らせる。

### S-11答えが空の旧クイズメモは、答えを入れるまで質問側の編集も保存されない

- 根拠：`MainActivity.kt` EditScreen の `persist` は質問・答えの両方が非空のときだけ保存する。開いた直後から空警告も表示される。
- 再現条件（仮説）：v0.3.x 由来で答えが空のクイズメモを開く → 質問だけ直しても保存されず、警告が常時出る。旧データにその形が実在するかは未確認のため仮説とする。
- 解消条件：質問と答えを独立に保存できるようにするか、空の答えを持つ旧メモの扱いを移行時に決める。

### S-12SPEC §5.1 のクイズプレビュー記述が曖昧で、実装と読みが合わない

- 根拠：SPEC §5.1 は「クイズ形式メモは下段ではプレビューを出さない」と読め、上段では出すとも読める。実装は上段でもプレビューなし（答えの表示回避として妥当）。また下段のクイズメモには形式を示す表示が何もない。
- 解消条件：SPEC の文面を実装どおり（両段ともプレビューなし）に明確化する。下段クイズメモへの形式表示の要否も合わせて決める。

## 良い点（維持すべき点）

- **保存の原子性と復旧経路**：tmp→fsync→prev 退避→rename の本経路に、B-3 修正（代替経路 rename）が維持されている。破損ファイルの退避（`.corrupt-<時刻>`）、正当な全消去（空＋skipped=0）を破損と誤認しない区別も正しい。
- **Manifest の健全さ**：`allowBackup="false"`（B-1 解消状態を維持）、権限なし、exported はランチャー Activity のみ。
- **SPEC 不変ルールの遵守**：`editBody` は reviewStage／lastReviewedAt／enteredActiveAt に触れない。上段メニューに削除なし。自動消滅なし。defer は到達・未到達どちらの分岐でも willDoAt を null に戻す。
- **ソート仕様の一致**：Tier −1／0／1／2 の優先順位、同率時タイブレーク（Tier 1 は比率上限 2.0→lastReviewedAt 古い順、Tier 0 は enteredActiveAt 新しい順）、stage の上限・下限（coerceIn）が SPEC §4・§7 と一致し、単体テストでも裏づけられている。
- **時刻の後方ジャンプ対策**：`maxSeen` 永続化によるガードは後方ジャンプには有効（前方については S-1）。
- **ID の一意性**：新規 ID は既存最大値＋1 で採番され、スナップショット復元との衝突がない。
- **ART_DIRECTION の数値基準**：スポットチェックした全テキスト／色ペアが 4.5:1 以上、最小フォントは 12.5sp（基準 12sp 以上）、赤系カラーは不使用。
- **移行の丁寧さ**：v0.3.x の4状態すべてに移行経路があり、文字列 "null" のガードや stage の範囲丸めも含めてテストで固定されている。
- **検証基盤**：アプリ本体を組み立てる回帰テスト（v0.6.0 の白画面事故の再発防止）、大文字フォントのゴールデンなど、実機なし検証が機能している。
