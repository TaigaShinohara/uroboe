## 判定

**不合格（要修正）**

根拠：致命的な問題（起動不能・データ喪失級）は無い。しかし、プロジェクト自身が正本に明記した数値基準（ART_DIRECTION.md「全テキストでコントラスト 4.5:1 以上」）に反する箇所が計算で確定した重大指摘1件（U-1）と、利用者が毎回目にする実文言が実在しない操作名で案内・通知している重大指摘1件（U-2）がある。必須修正が残るため合格にはできない。

- 指摘件数：全14件（致命的 0／重大 2／中 3／軽微 9）
- 計算値について：コントラスト比は WCAG 2.x の相対輝度式で算出した。実測（実機・ツール計測）による反証があれば、その結果で解消判定を更新してよい。

## 指摘一覧

### U-1詳細画面ボタンのキャプションがコントラスト基準（4.5:1）を満たさない

- 根拠：`MainActivity.kt:1128`。`DetailActionButton` のキャプションは `LocalContentColor.current.copy(alpha = 0.75f)` で描かれる。WCAG 式で実効コントラストを計算すると、Filled（ピンク地に白75%）＝ **3.82:1**、Tonal（ピンク淡地にピンク75%）＝ **3.55:1**、Danger（紙地に濃い橙75%）＝ **3.58:1** で、いずれも 4.5:1 未満。適合するのは Outlined（6.51:1）のみ。キャプションの文字サイズは bodySmall 12.5sp で、大きな文字の緩和条件（14pt太字以上等）にも当たらない。
- 何が問題か：ART_DIRECTION.md は「全テキスト WCAG AA 4.5:1 以上」を数値基準として明記している。その基準に、v0.6.0 の中核改善である「押すとどうなるかの一言」そのものが反している。読むべき理由が最も強い文字が、画面で最も読みにくい文字になっている。ゴールデン `edit_due.png` でも、キャプションは主ラベルに対して明確に薄く写っている。
- 解消条件：4種すべてのボタンでキャプションの実効コントラストが 4.5:1 以上になること（alpha の引き上げまたは色の直接指定で達成し、計算値または実測値を記録すること）。

### U-2旧操作名「またあとで」が実文言に残り、実在しないボタン名で案内・通知している

- 根拠：現在の UI に「またあとで」という項目は存在しない（実在は「まだやらない」）。にもかかわらず次の実文言が旧称のままである。
- 通知：`MainActivity.kt:402` ホームの長押しメニューで「まだやらない」を選んだ結果が「「またあとで」に送りました」と通知される。同じ操作を詳細画面から行うと `:340` で「「まだやらない」にしました」と正しく通知される。**同じ操作の結果通知が、入口によって違う言葉**になっている。
- About：`MainActivity.kt:554`「メモを長押しするとメニューが出て、「またあとで」「いつかやればいい」…へ分けられます」
- オンボーディング4枚目：`MainActivity.kt:1497`「「またあとで」「いつかやればいい」（保留）「やった」を選べます」
- 仕様側にも残存：`docs/SPEC.md:17`（§1）、`:126`（§5.4 要約）、`:163`（§8 検証条件。ここには旧名「できた」とスワイプ前提の「（右）」「（左）」も残っている）
- 何が問題か：案内文は「押すべきボタンを探すための地図」である。地図に実在しない地名が載っていると、利用者はメニューを開いて「またあとで」を探すことになる。通知文は操作のたびに出るため、目にする頻度も高い。文言の一貫性は本アプリの「迷わずさばける」というコンセプト体験の土台である。
- 解消条件：利用者が目にする文言（通知・About・オンボーディング）から「またあとで」が無くなり、実在の項目名「まだやらない」に統一されること。同じ操作の通知文が入口によらず同一になること。仕様書側の旧称・旧操作（スワイプ左右・「できた」）も現行に合わせて更新されること。

### U-3触覚の2段ルール（SPEC §5.0）と実装の対応が取れていない

- 根拠：SPEC §5.0 は「重い確定＝長押し起動／『やった』／削除・全消しの確定／『はじめる』」「軽い確認＝タップで開く／メニュー選択／FAB／元に戻す／ページ前進」と定める。実装は次の点で対応していない。
- (a) 長押しメニューの項目は `MenuActionRow`（`MainActivity.kt:685`）が一律 `TextHandleMove`（軽）を返すため、メニューの「やった」も軽い。一方、詳細画面の「やった」は `LongPress`（`:1388`、`:1426`）。**同じ「やった」が入口によって重さが違う**。メニューの「やった」はその場で操作が完結するため、詳細側と揃えるなら重い側のはずである。
- (b) オンボーディングのタイプ選択が `LongPress`（重）（`:1562`）。選択という軽い操作に対して重い側が使われており、2段ルールの表にもタイプ選択の位置づけが無く、根拠が正本に記録されていない。
- なお適合している部分：長押し起動＝LongPress（`:739`）、カードタップ＝軽（`:744`）、FAB＝軽（`:382`）、元に戻す＝軽（`:476`）、削除確定＝LongPress（`:509`）、全消し確定＝LongPress（`:533`）、つぎへ＝軽（`:1613`）、はじめる＝LongPress（`:1624`）。
- 何が問題か：v0.7.0 の売りは「操作の重さと触覚の一致」であり、不一致はそのまま体験の嘘になる。特に (a) は、最も頻繁に使う入口（長押しメニュー）で起きている。
- 解消条件：SPEC §5.0 の2段表に全操作（タイプ選択・メニュー項目を含む）が対応づけられ、同じ操作は入口によらず同じ重さになること。意図的に重さを変える操作があれば、その根拠が正本に明記されること。

### U-4OS の「動きを減らす」設定への追随がない

- 根拠：アニメーション関連の実装（画面遷移、押下スケール、状態行フェード、答えの展開、ドット伸縮等）はあるが、`ANIMATOR_DURATION_SCALE` 等、システムのアニメーション設定を参照するコードは存在しない（`app.uroboe` 配下を grep し 0 件）。
- 何が問題か：v0.7.0 で動きが増えた分、前庭障害や動きに敏感な利用者への配慮の欠落も増えた。minimal_information_design の検証観点「動きを止められる前提で作る（OS の設定に従い即時表示へ切り替える）」に反する。動きは補助であり、止めた状態でも内容が完全に伝わる設計が前提になる。
- 解消条件：システムのアニメーション無効／縮小設定時に、遷移・段階表示が即時表示へ切り替わること。または未対応であることが正本に明記され、実機確認項目に載ること。

### U-5フォント拡大・狭幅での詳細ボタン表示が未検証（仮説を含む）

- 根拠：`DetailActionButton` の主ラベル・キャプションはともに `maxLines = 1` ＋ `TextOverflow.Ellipsis`（`MainActivity.kt:1117-1131`）。SPEC 受け入れ条件10は「狭幅（360dp）＋フォント拡大で編集画面下部ボタン…が崩れず」と定めるが、`docs/UI_VERIFICATION.md` のゴールデンは標準サイズ・標準フォントのみで、拡大条件の記録がない。
- 何が問題か：「次は約30日後に浮上」のような長いキャプションは、360dp の2列配置＋フォント拡大では切れる可能性が高い。切れれば v0.6.0 の中核改善（押す前に結果が分かる）が、その条件の利用者には届かない。現行ゴールデン `edit_due.png`（約1日後）では収まっているため、これは未検証の仮説である。
- 解消条件：360dp・フォントスケール拡大の条件で詳細画面を描画し、主ラベルとキャプションが欠けずに読めることが記録されること（収まらない場合は折り返し等の対処とその記録）。

### U-6同じ移動操作に2系統の名前（セクション名と空間語）が混在する

- 根拠：長押しメニューは「そろそろやろうへ戻す」「いつかやればいいへ」、詳細画面は「上段へ戻す」「下段へ」（キャプションで正式名を補う）。ホームのセクション見出しは「そろそろやろう」「いつかやればいい（自動浮上なし）」であり、正式名はセクション名側である。
- 何が問題か：「上段」が「そろそろやろう」のことだと分かるのは、両方を見た利用者だけである。詳細側だけ空間語なのは非対称で、初見では対応づけに一拍かかる。
- 解消条件：名称をどちらかに統一すること。併用が意図なら、その意図が正本に明記されること。

### U-7オンボーディング4枚目のメニュー説明に、実際の項目「そろそろやる」が無い

- 根拠：`MainActivity.kt:1497`。4枚目は長押しメニューの項目として「またあとで」「いつかやればいい」「やった」を挙げるが、実際のメニューの先頭項目「そろそろやる」が挙がっていない（「そろそろやる」は後段の「開いた画面では…」で詳細画面の文脈で触れられるのみ）。U-2（旧称の残存）とは別に、項目の欠落の問題として分ける。
- 何が問題か：メニューを開く最も前向きな操作（やる宣言）が、使い方の説明で長押しメニューと結びついていない。利用者はメニューを開くまで「そろそろやる」がそこにあると知らない。
- 解消条件：4枚目の説明が、実際のメニュー項目（そろそろやる／まだやらない／いつかやればいいへ／やった）と過不足なく一致すること。

### U-8クイズカードの文言「タップで答えを見る」が実挙動とずれている

- 根拠：カードの注記（`MainActivity.kt:861` 付近「クイズ形式 ・ タップで答えを見る」）。実際はタップで詳細画面が開くだけで、答えは詳細内の「タップで答えを表示・編集」ボタン（`:1321`）をもう一度押すまで表示されない。
- 何が問題か：1タップで答えが出る期待を作り、実際は2タップかかる。互換表示の既存クイズメモだけに出る文言だが、文言と挙動の一致は信頼の単位である。
- 解消条件：文言が実挙動（開いた先で答えを表示できる）と一致すること。

### U-9カードの長押し操作に、読み上げ向けの判別材料がない（仮説を含む）

- 根拠：`MemoCardShell` の `combinedClickable` には `onClickLabel`／`onLongClickLabel` の指定がない。`contentDescription` の付与はアプリ全体で4箇所（FAB、戻る×2、編集を戻す）のみ。TalkBack では長押しアクションへ到達できる可能性はあるが、カードの読み上げから「長押しでメニューが開く」ことを判別する材料がセマンティクスに無い。
- 何が問題か：状態変更の唯一の入口が長押しメニューである設計では、その入口の発見可能性が視覚利用者だけでなく読み上げ利用者にも必要になる。未確認のため仮説として記録する。
- 解消条件：実機の TalkBack で、カードから長押しメニューへ到達でき、操作の意味が読み上げで判別できることが確認されること。

### U-10v0.7.0 の「状態1行のフェード切替」が、実際の遷移設計ではほぼ現れない

- 根拠：詳細画面の状態変更（そろそろやる／まだやらない／やった／下段へ／上段へ戻す）は、UroboeApp 側の各ハンドラがいずれも `detailId = null` にしてホームへ戻す（`MainActivity.kt:330-369`）。そのため `EditScreen` 内で状態行（`:1283-1299` の AnimatedContent）が切り替わるのは、開いたまま 60 秒更新で残り時間表示が変わるときくらいしかない。
- 何が問題か：SPEC §5.0 が v0.7.0 の動きとして掲げる「詳細画面の状態1行はフェードで切り替わる」は、体験としてはほぼ発生しない。設計意図と実態の記録がずれている。
- 解消条件：状態変更後も詳細に留まる設計に変えて切替が実際に現れるようにするか、SPEC §5.0 の記述を実態に合わせて修正すること。

### U-11ドキュメント（UI_CATALOG／SPEC §3／コードコメント）の陳腐化

- 根拠：
- `docs/UI_CATALOG.md` #8「破棄確認付き」：実装の書く画面に破棄確認は無い（自動保存＋全消しで自動破棄。SPEC §5.2 と実装は一致しており、カタログだけが古い）。
- 同 #12「フッター設定（縦3行）」：現行は「その他」ドロップダウンへの集約（SPEC §5.1 と実装が一致、カタログが旧形態のまま）。
- `docs/SPEC.md` §3 の状態図：長押しメニューの項目に「そろそろやる」が無い（§5.0 には明記があり、§3 が追随していない）。
- `MainActivity.kt` の `FloatingMemoMotif` のコメントが、実在しない引数 `highlightIndex` に言及している。
- 何が問題か：カタログと仕様は「次の変更の判断材料」であり、古い記述は次の設計判断を誤らせる。特に「破棄確認付き」は安全系の記述で、無いものがあると書かれているのは逆向きの誤りとして重い。
- 解消条件：各記述が現行実装と一致すること。

### U-12オンボーディング1・2枚目のモチーフが正本の色と一致しない（仮説を含む）

- 根拠：ART_DIRECTION.md は共通モチーフを「上の1本がピンクで浮かび上がる3本バー」と定めるが、オンボーディング1・2枚目では `elevatedTop = false` のため最上段がインク色 72%（`MainActivity.kt:588`、ゴールデン `onboarding_first.png` で目視確認）。ピンクになるのは3・4枚目と空状態のみ。
- 何が問題か：「浮上前→浮上」の段階表現という意図は推測できるが、正本に段階表現の記載が無く、字面では正本違反に見える。意図が記録されていない差異は、将来の変更で壊されても気づけない。
- 解消条件：段階表現が意図なら正本に明記すること。意図でないなら全ページで正本どおりに統一すること。

### U-13Undo バナーの「元に戻す」のタップ領域が小さい疑い（仮説）

- 根拠：バナー内 `TextButton` の `contentPadding` は vertical 2dp（`MainActivity.kt:484-488`）で、テキスト行高と合わせた実高は 48dp を下回る可能性がある（M3 の最小対話サイズで拡張される場合もあり、実機確認が必要）。バナーは snapshot 付き通知で 4.5 秒で自動消去される（`:247`）。
- 何が問題か：「消える前に、小さいボタンを正確に押す」は、誤操作からの回復手段としては負荷が高い。戻し損ねると完了・保留を取り消せない。
- 解消条件：実機でタップ領域が十分（目安 48dp）あること、または時間内に無理なく戻せることが確認されること。

### U-14下段カードの経過表示が「何からの経過か」を示さない

- 根拠：下段カードの経過は `MemoLogic.elapsedLabel(memo.createdAt, now)`（作成からの経過）で、「10日前」とだけ表示される（ゴールデン `home_with_memos.png` で目視確認）。下段の文脈では「保留してから」とも「書いてから」とも読める。なお下段への移動時刻 `lowPriorityAt` は保持されているが表示には使われていない。
- 何が問題か：数字の意味が曖昧だと、利用者は並び順（新しく保留した順）の根拠も読み取れない。情報の意味づけが1つ欠けている。
- 解消条件：経過の起点が利用者に判別できること（文言の工夫、または起点の定義が正本に明記され表示と一致すること）。

### 観察（指摘としない。意図的設計として正本に記録済みのため）

## 良い点（維持すべき点）

1. **最小文字サイズの遵守**：直書き・Typography とも最小は 12.5sp で、12sp 未満の文字は存在しない（コード全体を grep で網羅確認）。ART_DIRECTION の数値基準のうち、この項目は完全に守られている。
2. **コントラストの大部分は適合**：ピル（ピンク対ピンク淡 4.99:1）、長押しメニューのキャプション（5.49〜5.79:1）、保存失敗バナー（濃い橙対橙淡 5.14:1）、補助テキスト（薄インク対紙 6.26:1）はすべて 4.5:1 以上。赤を使わず濃い橙で統一する方針も全画面で一貫している。
3. **SPEC の不変ルールと実装の一致**：`MemoStore.editBody` は `reviewStage`／`lastReviewedAt`／`enteredActiveAt` に触れず、「閲覧・編集だけでは進めない／リセットしない」が守られている。「まだやらない」の未到達時に Fresh 猶予へ戻らない点、下段への移動で宣言（willDoAt）が解除される点も仕様どおり。上段の長押しメニューに削除を置かない不変ルールも守られている（削除は下段メニューと詳細のみ、確認ダイアログ経由）。
4. **情報の重複を避ける実装**：カードのプレビューは題名行を除いて表示し、1行目の二重表示を防いでいる（題名＋本文の実質重複の排除）。詳細画面の状態行（現在の状態）とボタンのキャプション（押した後の結果）は役割が分かれており、重複ではなく補完になっている。
5. **情報の集約と後出し**：低頻度機能はフッター「その他」に集約され、常駐の説明文は置かず、空文字の警告と残り字数だけが必要な時点で出る。minimal_information_design の「別場所へまとめる」「後出しにする」に沿った構成である。
6. **色だけに頼らない符号化**：オンボーディングのタイプ選択は地色＋枠＋「✓」の多重符号化、ピルは文言そのもので区別、下段の区別は面色＋見出し文言（「自動浮上なし」明記）で担保されている。
7. **Undo の堅牢さ**：通知は `MemoStore`（Application スコープ）に保持され画面回転で失われず、`LiveRegionMode.Polite` で読み上げにも配慮されている。保存の原子性（tmp→fsync→prev退避→rename）と起動時の自動復旧は、「勝手に消えない安心」というコンセプトの土台として実装で裏付けられている。
8. **空状態の導線が切れていない**：メモ0件でもフッター「その他」から About・書き出し・全消しに到達でき（ゴールデン `home_empty.png` で確認）、空状態の案内文は FAB の実ラベル「メモを書く」と一致している。

## コンセプト達成の照合

コンセプト：［メモは取るが二度と見返さない／よく忘れる／マルチタスクが苦手／期限に追われたくない人］が［思いついた時と、アプリを開いた時］に［分類なしで1行預け、浮かび上がったものを軽くさばく］ことで［勝手に消えない安心のまま、『いつかやろう』が『そろそろやろう』に変わる］体験。キャッチフレーズは「メモを不要にするメモ帳」。

| コンセプト要素 | 判定 | 根拠 |
|---|---|---|
| 誰（見返さない・忘れる・期限が苦手な人） | 実現 | 機能構成が対象に合っている：分類・フォルダ・期限・通知・ストリークのいずれも無く、罪悪感ギミックの排除が SPEC §1 の禁止事項と実装の両方で確認できる |
| 場面（思いついた時／開いた時） | 実現 | 書く入口は FAB 1タップ＋自動フォーカス＋自動保存で最短。開いた画面では忘却曲線ソート済みの一覧が即座に出る |
| 行為：1行預ける | 実現 | 書く画面は1欄のみ、分類・形式選択なし。最初の入力で作成され、戻るだけで確定する |
| 行為：浮かんだものを軽くさばく | 部分的に実現 | 浮上とさばく操作（長押しメニュー／詳細ボタン＋Undo）は実装されている。ただし長押しは画面内に手がかりが無く（ホームのヒント文は v0.5 で削除済み）、初見の利用者が発見できるかは未確認。文言の不一致（U-2）も「迷わずさばける」を損なっている |
| 気持ち：勝手に消えない安心 | 実現（仕組みとして） | 自動消滅なし、削除は確認ダイアログ経由、Undo あり、保存は原子的で自動復旧付き。オンボーディングとスキップ確認でも「消えずに残る」ことが明示される |
| 気持ち：『いつかやろう』が『そろそろやろう』に変わる | 未確認 | 変わる仕組み（浮上・宣言・完了）は実現しているが、体験として発生したかは SPEC §8 の実機・実メモによる段階検証が前提であり、本審査の資料範囲では判定できない |
| キャッチフレーズ「メモを不要にするメモ帳」 | 未確認 | 「やった」で一覧から外れる導線はあるが、メモが不要になっていく体験の実測・観察記録がない |

## 未確認の範囲

- 実機での触覚の強さ・心地よさ、カード押下スケールの体感、長押しメニューの開閉のテンポ（JVM 検証とコードでは判定できない）
- TalkBack での全フロー、特にカードから長押しメニューへの到達（U-9）
- 360dp＋フォント拡大でのレイアウトとキャプションの可読性（U-5）
- システムのダークモード設定時の見え方（テーマは light 系のみで固定されており、意図か未対応か正本に明記がない）
- 人間による初見確認（3秒テスト／無読テスト相当）：ホーム画面で長押しに気づけるか、詳細ボタンが迷わず押せるか
- SPEC §8 の段階検証全体（実メモ・実期間での浮上の「ちょうどよさ」、20〜50件蓄積時の視認性、完了体験の発生）
- 本審査はレビューのみで、ビルド・テストの再実行は行っていない（UI_VERIFICATION.md の記録は資料として参照した）
